# P0 — the item-level CPI foundation

`pipelines/p0_fetch.py` → tables `cu_item`, `cu_series`, `cpi_obs` (+ view `cpi_obs_latest`),
`cpi_weight`, `cpi_item_month`, `validation`; file `out/cpi_item_month.parquet`.
Run: `cd $CPI_ROOT && ./p0_fetch.py [--full] [--weights] [--force]`. The docstring prints the spec.

P0 is the data layer. Every other pipeline (P1–P10) reads the tables P0 builds and never
re-fetches BLS itself: P1/P2/P3 read `cpi_item_month`, `cpi_weight` and `cu_item`; P4 validates
its ALFRED vintages against `cpi_item_month.mom_sa`; P5 writes into the shared `validation`
table P0 creates. If P0's numbers are wrong, everything downstream is wrong, so the last thing
P0 does on every run is reconstruct the published all-items index from its own leaf data and
check it against BLS.

---

## Part 1 — in plain language

### What P0 does

It downloads the BLS Consumer Price Index flat files, keeps only the slice the rest of the lab
uses (US city average, monthly, CPI-U), stores every index observation with a vintage stamp so
revisions never overwrite history, attaches each item's spending weight, and derives one tidy
per-item-per-month table (`cpi_item_month`) with the index level, month-over-month, year-over-year
and a weight column. Then it validates itself.

Nothing here is an original measure. P0's only opinion is which rows to keep and how to arrange
them; the numbers are BLS's own, and the validation step is there to prove the arrangement did
not corrupt them.

### The self-check that everything rests on

BLS publishes the all-items index directly (`SA0`). P0 also holds, separately, the roughly
180 individual "leaf" items that make up that basket, each with its December spending weight.
So P0 can **rebuild** the headline from the parts and compare its rebuild to the published
whole. The rebuild is a December-chained Laspeyres index: within each weight year the leaves are
combined in proportion to their December relative-importance weights, anchored to the published
December level, and the resulting year-over-year rate is compared to the published year-over-year
rate for the most recent eight months.

At the last run the two agreed to within **−0.038 to +0.067 percentage points** across those
eight months (2025-12 through 2026-07), all inside the ±0.15 pp tolerance:

| month | reconstructed YoY | published YoY | diff |
|---|---|---|---|
| 2025-12 | 2.639 | 2.677 | −0.038 |
| 2026-01 | 2.349 | 2.386 | −0.037 |
| 2026-02 | 2.381 | 2.414 | −0.033 |
| 2026-03 | 3.277 | 3.256 | +0.021 |
| 2026-04 | 3.838 | 3.811 | +0.027 |
| 2026-05 | 4.315 | 4.249 | +0.067 |
| 2026-06 | 3.554 | 3.531 | +0.022 |
| 2026-07 | 3.371 | 3.365 | +0.006 |

That small residual drift is expected and disclosed: P0 recombines **published rounded item
indexes** with **published rounded relative-importance weights**, and it covers only the ~97% of
the basket that is a sampled published leaf (the rest is "unsampled" strata with no index, which
drop out and are renormalised away). It does not reproduce BLS's internal special aggregation
factors. So the replica tracks the headline to about a tenth of a point but is not bit-identical,
and P1/P2/P3 — which build their own re-weighted indexes with the *same* arithmetic so they stay
comparable to this replica — inherit exactly that drift as their floor. This is why the check
exists and why its tolerance is 0.15 pp rather than zero.

### What is in the basket, and what "leaf" means

The CPI item list is a tree: "All items" at the top, then "Food", then "Food at home", then
"Cereals and bakery products", down to individual things like "Bread". P0 needs the bottom of
each branch — the **leaf** items — because those are what carry independent price movement and
what the reconstruction sums over. Aggregates like "Food" are just weighted roll-ups of their
leaves, so including both would double-count.

P0 reconstructs the parent-of relationships from the item file's display levels, then marks an
item a leaf when it is a matched, non-special item that no other matched item claims as a parent.
At the last run this gave **175–182 leaves per weight year**, carrying **95.6–97.7%** of each
year's total weight (the missing few percent are the unsampled strata).

### Weights, and the "which year" rule

BLS restates the basket's spending weights once a year, using December relative importances.
The rule P0 encodes everywhere: **the December weights of year Y apply to the twelve months of
year Y+1.** So a 2026 month is priced with the December-2025 weights. This one convention is
repeated in `cpi_item_month`, in the validation, and in every downstream pipeline.

## Part 2 — technical appendix

### Sources and the slice kept

All data comes from the BLS time-series flat-file tree `https://download.bls.gov/pub/time.series/cu/`
(base URL `common.BLS_TS`). bls.gov returns 403 without a descriptive User-Agent, so every
download goes through `common.fetch`, which sets `UA = "cpilab/0.1 (+https://github.com/bristlecone-public/bristlecone)"`.

- **Dimensions**: `cu.item` (the item tree) and `cu.series` (the series catalogue), loaded by
  `load_dims`.
- **Observations**: by default only `cu.data.0.Current`. `--full` additionally pulls the eleven
  full-history files (`cu.data.1.AllItems`, `cu.data.2.Summaries`, and the nine
  `cu.data.11–20.US*` topic files; `FULL_FILES`, ~300 MB once). The live DB currently holds full
  history — `cpi_obs` observations run **1913–2026** — so `--full` has been run at least once.

The kept slice is defined in `load_dims`: `area_code == "0000"` (US city average),
`periodicity_code == "R"` (monthly), and `series_id` starting with `"CU"` (CPI-U — `CUUR*`
seasonally-unadjusted, `CUSR*` seasonally-adjusted; CPI-W `CW*` is excluded). `load_data` keeps
only monthly periods (`period` starting `"M"`) and drops the `M13` annual-average pseudo-period.
Live counts: `cu_item` **400** items; `cu_series` **726** series (**400** NSA `U` + **326** SA `S`);
`cpi_obs` **388,519** observation-vintage rows.

### Fetch and caching

`common.fetch(url, dest, force, retries=3)` does a `HEAD` first and compares `Last-Modified`
against a `.lm` sidecar file; if unchanged (and not `--force`) it returns the cached file and
reports `changed=False`, and P0 skips reprocessing that file. It retries 3 times with linear
backoff and raises if all fail.

### Vintaged observations

`cpi_obs` is append-only per vintage: `PRIMARY KEY(series_id, year, period, pull_id)`, where each
`load_data` run of each file gets a fresh `pull_id` from `new_pull`. On each file, P0 reads the
current values, joins against the `cpi_obs_latest` view (the max-`pull_id` value per
series/month), and **only inserts rows whose value differs from the stored latest by > 1e-9**.
So a monthly re-download that changes nothing writes nothing, and a BLS revision is recorded as a
new vintage beside the old one rather than clobbering it. Downstream code reads `cpi_obs_latest`,
never `cpi_obs` directly.

### Item tree and leaf detection

`load_dims` sorts items by `sort_sequence`, then walks the `display_level` column to assign each
row a `parent_code` (the nearest preceding row one level shallower), stored on `cu_item`.

Leaves are assigned in `load_weights`, not from the tree in isolation, because only *matched*
weight rows matter: `main_codes` = matched main-section items; `parents_used` = the set of their
parents; an item is a leaf (`is_leaf = 1`) when it is a matched main-section row whose code is
**not** in `parents_used`. This is the operational definition the whole lab uses via
`cpi_weight WHERE is_leaf=1 AND matched=1`. Live leaf counts / leaf-weight sums by year:

| weight_year | rows | matched | leaves | leaf weight sum |
|---|---|---|---|---|
| 2017 | 321 | 299 | 182 | 97.67 |
| 2018 | 321 | 299 | 182 | 97.66 |
| 2019 | 321 | 299 | 182 | 97.56 |
| 2020 | 321 | 292 | 175 | 95.58 |
| 2021 | 321 | 293 | 176 | 96.28 |
| 2022 | 321 | 293 | 176 | 96.14 |
| 2023 | 321 | 296 | 179 | 97.23 |
| 2024 | 321 | 296 | 179 | 97.28 |
| 2025 | 321 | 296 | 179 | 97.65 |

(Weight years 2017–2019 are back-filled by P1's `extend_weights`, not by P0 — see P1.md — but
they live in P0's `cpi_weight` table and P0's `build_item_month` consumes them.)

### Weights: parsing relative-importance tables

`load_weights` fetches the annual relative-importance HTML page
`https://www.bls.gov/cpi/tables/relative-importance/{y}.htm` (default years 2020 through the
current year; the pre-2020 pages do not exist and are handled by P1). Because the HTML markup
varies year to year, P0 does **not** trust the page's own hierarchy — it matches each table row's
item **name** back to a `cu_item` code and takes level and parentage from `cu_item`. Names are
normalised (`norm`: HTML-unescape, lowercase, strip footnote markers `(n)` and punctuation). The
first two numeric cells are read as CPI-U weight (`weight_u`) and CPI-W weight (`weight_w`). Rows
after a "Special aggregate indexes" marker are tagged `section = 'special'` and excluded from the
leaf set.

**Name-ambiguity fallback (a documented weak point).** When a normalised name matches exactly one
`cu_item` code, that code is used. When it matches **more than one** code
(`p0_fetch.py` ~line 128), P0 prefers a candidate whose parent has already been matched earlier in
the same section, and **otherwise falls back to `cands[0]`** — the first candidate in item order.
This is a heuristic, not a guaranteed-correct disambiguation; a mis-tie would attach a weight to
the wrong code. The count of ambiguous rows is logged each run (`%d ambiguous`). Names that match
no code are recorded unmatched with a placeholder code `"?" + name`, `matched = 0`, and logged.

### Derived table `cpi_item_month`

`build_item_month` pivots `cpi_obs_latest` (joined to `cu_series`) into one row per
`(item_code, ym)` with NSA and SA index levels, then computes rates. Live: **225,102** rows,
`ym` from **1913-01** to **2026-07**.

All lags are **calendar-aligned**, not row offsets — the `lag()` helper shifts a `PeriodIndex` and
re-merges — precisely so the October-2025 gap (no CPI release that month, government shutdown) does
not silently misalign a row-based `shift`. Consequences: `mom_sa`/`mom_nsa` = 1-month change,
`yoy` = 12-month NSA change, `ann3m` = 3-month SA change annualised (`(idx/lag3)**4 − 1`); the
month after a gap is NaN by design.

The `weight` column merges `cpi_weight` (matched rows) on the Y→Y+1 rule
(`w["yr"] = weight_year + 1`). `contrib_yoy = weight × yoy / 100` is an **approximation** of an
item's contribution to headline YoY (code comment: "proper BLS method uses relative importance
updated by relative price change; this is close for a spec table"). Treat `contrib_yoy` as
indicative, not the official effect. The table is fully rewritten each run and also dumped to
`out/cpi_item_month.parquet` (~7.7 MB) — P0's only file artefact. Unlike downstream pipelines, P0
writes **no `out/<name>.json`**; its consumers read the DB tables.

### Validation: December-chained Laspeyres vs published CPI-U

`validate` is the load-bearing check. Over `is_leaf=1 AND matched=1` leaves it forms, for each
month of weight year Y+1,

&nbsp;&nbsp;&nbsp;&nbsp;*I<sub>t</sub>* = *I*<sub>Dec(Y)</sub> · Σ*<sub>i</sub> w<sub>i</sub> P<sub>it</sub>/P<sub>i,Dec(Y)</sub>* / Σ*<sub>i</sub> w<sub>i</sub>*

where *w<sub>i</sub>* is the December relative importance, *P* is the leaf's NSA index, and
*I*<sub>Dec(Y)</sub> is the **published** `SA0` December level (so each year is re-anchored to the
published December, then Laspeyres-extrapolated). It compares the reconstructed year-over-year
rate to the published `SA0` year-over-year rate for the **last 8 months**, flags each
`abs(diff) < 0.15` (pp), writes every month to the `validation` table under
`check_name = 'dec_chained_laspeyres_yoy'`, and the script **exits 2** if any month fails (tables
and parquet are still written). The published side is BLS's own `SA0` NSA index carried straight
through `cpi_obs` → `cpi_item_month`, so this is a genuine parts-vs-whole check, not a tautology.
Last run: all 8 months OK (the table above). Per-month leaf coverage is logged alongside each row.

### Schema (from `common.py`)

```sql
cu_item(item_code PK, item_name, display_level, selectable, sort_sequence, parent_code)
cu_series(series_id PK, area_code, item_code, seasonal, periodicity_code, base_code,
          base_period, series_title, begin_year, begin_period, end_year, end_period)
cpi_obs(series_id, year, period, value, footnote, pull_id, PRIMARY KEY(series_id,year,period,pull_id))
cpi_obs_latest  -- VIEW: the max(pull_id) value per (series_id, year, period)
cpi_weight(weight_year, item_code, item_name, weight_u, weight_w, matched, section,
           level, is_leaf, PRIMARY KEY(weight_year, item_code))
cpi_item_month(item_code, ym, idx_nsa, idx_sa, mom_sa, mom_nsa, yoy, ann3m, weight,
               contrib_yoy, PRIMARY KEY(item_code, ym))
validation(run_at, check_name, ym, ours, published, diff, ok)
pulls(pull_id PK, pulled_at, source, note)
```

SQLite in WAL mode (`common.db`). `init_db` is idempotent (`CREATE TABLE IF NOT EXISTS`).

### Known limitations

1. **The replica is not bit-identical to BLS.** It recombines rounded published item indexes with
   rounded published weights over the ~97% sampled-leaf basket, without BLS's internal special
   aggregation factors, so a ~0.1 pp drift is structural. Every P1/P2/P3 index built on the same
   arithmetic inherits it. This is disclosed, not a bug — hence the ±0.15 pp tolerance.
2. **`contrib_yoy` is an approximation** (`weight × yoy / 100`), not the official relative-importance
   contribution. Do not present it as the exact effect on the headline.
3. **Weight name-matching can mis-tie.** When a relative-importance row's name maps to more than one
   `cu_item` code and no parent is yet matched, P0 falls back to the first candidate in item order.
   Ambiguous/unmatched counts are logged; a mis-tie would misattach a weight.
4. **Item composition changes over time.** Titles changed in Jan 2026 and series were rebased in
   Apr 2026, and older weight years carry items that no longer exist as published leaves. All
   joins are on codes, never titles; leaf sets differ by year (175–182 above).
5. **October 2025 has no CPI.** Rates are calendar-aligned so the gap produces NaNs rather than a
   silent row shift, but any month adjacent to a gap is NaN by design.
6. **CPI-U only, US city average only.** Metro-area rows and CPI-W are filtered out at ingestion;
   a pipeline needing metro data (e.g. P9) must load it into its own table, not widen `cpi_obs`.

### Re-running / cron

```
$CPI_ROOT/p0_fetch.py            # dims + cu.data.0.Current; weights loaded if the table is empty
$CPI_ROOT/p0_fetch.py --full     # also pull the 11 full-history files (~300 MB, once)
$CPI_ROOT/p0_fetch.py --weights  # refresh the annual relative-importance tables
$CPI_ROOT/p0_fetch.py --force    # bypass the Last-Modified cache and re-store
```

Idempotent. `build_item_month` + `validate` run only when `load_data` reported new/changed data
(or under `--force`/`--weights`); otherwise the script logs "nothing new" and exits 0. In
`pipelines/run_monthly.sh` P0 is the gate that the "new CPI data" branch (P1 → P2 → P3 → P10)
runs behind, with a separate February `--weights` refresh chain. Exit code 2 signals the
self-validation drifted past ±0.15 pp; the tables and parquet are still written.
